# Performance Engineering

M14 makes performance claims reproducible instead of rhetorical.

Run the benchmark matrix:

```powershell
cargo run -p azums --release --bin azums-perf
```

Default output:

- `target/azums-perf/m14_report.json`
- `target/azums-perf/m14_report.md`

## Configuration

| Variable | Default | Meaning |
|---|---:|---|
| `AZUMS_PERF_BACKENDS` | `memory,sqlite` | Comma-separated backends. Use `postgres` with `DATABASE_URL`/`TEST_DATABASE_URL`, and `redis` with `REDIS_URL`. |
| `AZUMS_PERF_JOBS` | `10000` | Jobs per non-idle scenario. |
| `AZUMS_PERF_ITERATIONS` | `5` | Repeated samples per scenario. |
| `AZUMS_PERF_BATCH_SIZE` | `64` | Lease batch size. |
| `AZUMS_PERF_OUTPUT_DIR` | `target/azums-perf` | Report directory. |

## Matrix

The M14 harness measures:

- backends: Memory, SQLite, PostgreSQL when configured, Redis when configured
- worker counts: 1, 2, 4, 8, 16, 32
- workloads: small jobs, large payloads, batch jobs, mixed priorities, high contention, idle queue
- throughput: jobs/sec
- latency: p50, p95, p99, p99.9 across scenario iterations
- resources: explicit nullable resource fields, plus conditions explaining what was and was not measured

## Fairness Rules

Performance claims must include:

- command used
- backend URLs or statement that a backend was skipped
- worker count
- job count
- iteration count
- batch size
- build profile
- machine/OS/architecture
- whether CPU, RAM, allocations, disk I/O, and network I/O were measured or left null

A number like `380k jobs/sec` is credible only when attached to a report generated by this harness or an equivalent independently runnable benchmark artifact.

## Supporting Microbenchmarks

Criterion remains useful for small hot-path checks:

```powershell
cargo bench -p azums --benches
```

Use Criterion for regression detection and `azums-perf` for end-to-end comparison across backend, worker, and workload dimensions.
